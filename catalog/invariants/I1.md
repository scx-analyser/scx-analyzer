# I1 — Locking requirements for protected scheduler-state writes (v7.1)

Machine-readable form: [`I1.yaml`](I1.yaml). Kernel: Linux **v7.1**
(`8cd9520d35a6c38db6567e97dd93b1f11f185dc6`), which matches the course kernel. All `file:line` references are for that commit.

**Invariant.** When a sched_ext kfunc modifies shared scheduler state, directly or along its kernel call path, the write
happens with the lock (or guard) that protects that state held. This is checked per write site, not per kfunc
calling context. Calling-context rules (BTF sets, callbacks, program types) are not the invariant. They are kept as
supporting **entry state**: the locks already held when a kfunc's path starts, which the lockset analysis (C2/C3)
needs as its seed.

`I1.yaml` has one family `I1` (checker plug-ins register as `I1`) with two kinds of rules:

* **7 protection rules** (`role: protection`). Each **obligation** binds one write (struct, fields, object instance,
  op) at named source sites to the specific lock instance or predicate it needs, with a `basis` and kernel evidence.
* **13 entry-state rules** (`role: entry_state`). These cover all 59 kfuncs: allowed contexts and callback-entry locks.

`basis`: `checked` = lockdep assertion or production runtime check on every path; `documented` = a kernel comment
states the rule; `observed` = the lock is taken on every inspected path but no rule is stated; `hypothesis` = not
established (draft rules only). `source_verified` means that every cited line was checked. It is not a claim that a
proposed requirement holds.

The task-rq requirement for `scx_bpf_task_set_*` used to sit in a verified rule. It is now only in the draft rule.
The setters use RCU, a scheduler-authority check and plain stores (8844-8878). This proves neither a race nor that
no synchronization is needed.

## 2. Worked example: `scx_bpf_dsq_move_to_local` end to end

`scx_bpf_dsq_move_to_local(dsq_id)` (8555) calls `___v2(dsq_id, 0)` (8512). It is in the dispatch set only. In
`I1.yaml` it is encoded as fully bound obligations with `paths` (`I1.nonlocal_dsq.dsq_lock/unlink_dsq`,
`I1.local_dsq.rq_lock/move_local_*`, `I1.rq_scx.rq_lock/extra_enq_flags`, `I1.ops_state.atomic/dispatch_claim_cmpxchg`).

```
entry  balance_one(rq)                       2890 lockdep_assert_rq_held(rq); 2891 rq->scx.flags |= IN_BALANCE   held {rq}
       scx_dispatch_sched                    2827 dspc->rq = rq; 2844 SCX_CALL_OP(dispatch, rq) (update_locked_rq 465)
       BPF ops.dispatch -> kfunc
root   scx_bpf_dsq_move_to_local___v2        held {rq = dspc->rq}
 (a)   8530 flush_dispatch_buf(sch, dspc->rq) -> 2757 finish_dispatch()                  held {rq}
         2724 try_cmpxchg ops_state QUEUED->DISPATCHING  (claim; qseq captured at 8145, checked 2708)
         2746 dispatch_enqueue(non-local)  1529 lock dsq -> list/nr/seq/p->scx.dsq ... 1635 unlock -> 1643 set_release NONE
         2744 dispatch_to_local_dsq        rq lock dance, 2622 set_release NONE
 (b)   8538 consume_dispatch_q(sch, dspc->rq, dsq, enq_flags)                             held {rq}
         2525 raw_spin_lock(&dsq->lock)                                                    held {rq, dsq}
         same rq (2541):  2542 task_unlink_from_dsq   writes dsq->list/priq/nr/first_task, p->scx.dsq_list
                          2543 move_local_task_to_local_dsq  asserts dsq+rq (2256-2257)
                               2262/2264 local_dsq.list, 2266 local_dsq.nr (1370), 2267 p->scx.dsq
                          2544 unlock dsq                                                   held {rq}
         remote (2548-2549): consume_remote_task  2430 unlock this_rq                       held {dsq}
                          unlink_dsq_and_lock_src_rq 2412 assert dsq; 2415 task_unlink_from_dsq; 2416 holding_cpu
                          2418 unlock dsq; 2419 lock src_rq                                  held {src_rq}
                          move_remote_task_to_local_dsq 2284 assert src_rq; 2290 sticky_cpu; 2294 unlock src_rq,
                          2295 lock dst_rq(=this rq); 2304-2306 dst_rq->scx.extra_enq_flags   held {dst_rq}
       8545 dspc->nr_tasks++ (per-CPU)       returns with this rq held again
```

Every protected write on this path has its protecting lock held. The interesting step is the remote branch: there
the DSQ unlink at 2415 runs with **only** the DSQ lock (this rq was dropped at 2430). This is why the unlink
obligation names `dsq->lock` and not an rq lock. After 2416, `holding_cpu` hands the task over to the
`src_rq` lock (comment 2378-2404).

## 3. Supporting entry state (not the invariant)

The entry-state rules keep the verified context material for C2/C3. Fixes in this revision:

* Kfuncs that are in two BTF sets use `contexts_any_of`, so alternatives are never combined: `dsq_move*` (dispatch | unlocked)
  and the select_cpu kfuncs (select_cpu | unlocked).
* `scx_bpf_locked_rq` (`I1.locked_rq.getter`) is separated from `scx_bpf_cpuperf_set`. The setter accepts
  `locked_rq == NULL` and takes the target rq itself, and it now lives in `I1.rq_scx.rq_lock`.
* `ops.cgroup_cancel_move` does **not** hold `scx_cgroup_ops_rwsem` on entry. Its call sites,
  `scx_cgroup_can_attach` (error path, ext.c:4389) and `scx_cgroup_cancel_attach` (4430), take no rwsem. Only
  `cgroup_set_weight/idle/bandwidth` take it, in read mode (`percpu_down_read` 4440/4456/4473). The write side is
  `scx_cgroup_lock` (4500).
* `ops.init_task` is entered without an rq lock. It may sleep (sleepable member, ext.c:7616; "This operation may
  block", ext_internal.h:570), it is called with `locked_rq = NULL` (3572), and the fork path drops `pi_lock`
  before `scx_fork()` (core.c:4783). The other three callers call it after `scx_task_iter_unlock()`
  (6996, 7291, 5807).
* `not_held` at `callback_entry` is the precondition of the cited call sites. It is not an object-specific absence fact for
  every ambient rq: a NULL `locked_rq` argument neither releases an rq nor clears the tracked one (474-485).
* Idle cpumask kfuncs: KF_ACQUIRE/KF_RELEASE only make the pointer verifier-tracked and trusted. No reference is
  acquired (ext_idle.c:1241-1248).

| Callback | Locks held on entry (call site) | Context-sensitive sets |
|---|---|---|
| select_cpu | `p->pi_lock`, no rq passed (3339) | select_cpu, enqueue_dispatch |
| enqueue | `rq(task_rq(p))` (1948) | select_cpu, enqueue_dispatch |
| dispatch | `rq(this cpu)`, `SCX_RQ_IN_BALANCE` (2840/2844) | enqueue_dispatch, dispatch |
| cpu_release | `rq(this cpu)` (3054) | cpu_release |
| other task ops, cpu_acquire, update_idle | the callback's rq; exit_task also `pi_lock` | — |
| dump_cpu / dump_task | `scx_dump_lock` + dumped CPU's rq (6381) | — |
| dump | `scx_dump_lock` (6337), no rq | unlocked |
| init_task | no rq (see above) | unlocked |
| cgroup_set_weight/idle/bandwidth | `scx_cgroup_ops_rwsem` read | unlocked |
| cgroup_cancel_move | no `scx_cgroup_ops_rwsem` (4389, 4430) | unlocked |
| other UNLOCKED ops | no rq passed | unlocked |
| SYSCALL / TRACING prog | no tracked locks / arbitrary | unlocked, select_cpu, idle, any / idle, any |

## 4. Gaps and suggested tests

1. TRACING programs may call `scx_bpf_cpuperf_set` while the core holds an rq outside an SCX op. `scx_locked_rq()`
   is NULL there, so the kfunc would call `rq_lock_irqsave()` (9453) on a possibly held rq. *Test.*
2. The draft slice/vtime writes: concurrent `scx_bpf_task_set_slice` from TRACING versus `update_curr_scx` (1348). *Test.*
3. `scx_dsq_move()` infers "this rq held" from `SCX_RQ_IN_BALANCE` (8389). This is correct only while
   ops.dispatch is the only rq-locked caller.
4. Dispatch-only kfuncs have no runtime context check (`dspc->rq`, 8530), for example when called from async callbacks. *Hypothesis.*
5. lockdep-only checks (`move_local_task_to_local_dsq` 2256, `reenqueue_local` 8738, preamble 8102) enforce nothing in production.

For Epic B/C: compile only `checked` / `documented` obligations. Resolve `when` and the instance expressions per
site, or report UNKNOWN. Seed entry locksets from the entry-state rules.
