# I1 — Calling context & locking requirements of sched_ext kfuncs (v7.1)

Machine-readable form: [`I1.yaml`](I1.yaml) (14 entries, ids `I1.<group>.<aspect>`, all 59 sched_ext kfuncs covered).
All `file:line` references are for Linux **v7.1** (`KERNEL_VERSION`).

## 1. The v7.1 context model

**There is no runtime `kf_mask` check any more.** Older kernels tracked `current->scx.kf_mask` and called
`scx_kf_allowed()` inside kfuncs. In v7.1, `struct sched_ext_entity` only has `kf_tasks[2]`
(`include/linux/sched/ext.h:201`), and per-callback restrictions are applied **only by the verifier**:

* Each kfunc group is a BTF set with `.filter = scx_kfunc_context_filter`. The sets are
  `enqueue_dispatch` (ext.c:8331), `dispatch` (ext.c:8696), `cpu_release` (ext.c:8745), `unlocked` (ext.c:8814),
  `any` (ext.c:9767), `idle` (ext_idle.c:1468) and `select_cpu` (ext_idle.c:1499).
* Which BPF program types can see a set depends on registration (ext.c:9936-9951, ext_idle.c:1515-1519):
  STRUCT_OPS sees all of them, SYSCALL sees `unlocked`/`select_cpu`/`idle`/`any`, TRACING sees `idle`/`any`.
* `scx_kfunc_context_filter()` (ext.c:9860-9918) runs from `btf_kfunc_is_allowed()` (verifier.c:12612, btf.c:8864).
  For a `sched_ext_ops` program it looks up `scx_kf_allow_flags[SCX_MOFF_IDX(attach_st_ops_member_off)]`
  (table at ext.c:9828-9850). `any` and `idle` kfuncs are always allowed (ext.c:9900). Non-SCX struct_ops are denied (ext.c:9896).
* A kfunc that is in more than one set is allowed when **any** of its sets is allowed. This happens for
  `scx_bpf_dsq_move*` (dispatch + unlocked) and the select_cpu kfuncs (select_cpu + unlocked).
* Sleepability: `bpf_scx_check_member()` (ext.c:7609-7631) allows sleepable programs only on the ops marked "Y" below.
  The verifier rejects a `KF_SLEEPABLE` kfunc (only `scx_bpf_create_dsq`) in a non-sleepable program (verifier.c:13053).
* No SCX kfunc may be called while the program holds a `bpf_spin_lock` (verifier.c:17626-17634).

Runtime bookkeeping that kfuncs consult (it is not a permission mask):
`SCX_CALL_OP*` publishes the held rq in per-CPU `scx_locked_rq_state`. It does this with `lockdep_assert_rq_held`
(ext.c:456-485). `SCX_CALL_OP_TASK*` records the subject task(s) in `current->scx.kf_tasks[]` (ext.c:503-546),
which `scx_kf_arg_task_ok()` checks (ext.c:549-559). It also uses `rq->scx.flags & SCX_RQ_IN_BALANCE`,
`rq->scx.in_select_cpu` and per-CPU `direct_dispatch_task`.

## 2. Gaps and unenforced cases (candidates for the checker and tests)

1. **There is no runtime context check for dispatch-only kfuncs.** `scx_bpf_dsq_move_to_local`, `dispatch_cancel` and `nr_slots`
   use per-CPU `dsp_ctx` (`dspc->rq`, ext.c:8530). Only the verifier filter guarantees that we are inside `ops.dispatch`.
   The filter keys on the program's *attach member*. So any code the verifier treats as part of that program
   inherits its rights: subprogs, and possibly async callbacks (bpf_timer/wq) defined in the dispatch program.
   An async callback would run outside `balance_one()` with a stale `dspc`. *Hypothesis, needs a test.*
2. **`scx_dsq_move()` infers its locking from `SCX_RQ_IN_BALANCE`** (8389), not from `scx_locked_rq()`.
   This is only correct because the filter admits no other rq-locked op. Any future change to the allow table
   (for example adding `dsq_move` to `enqueue`) would silently self-deadlock.
3. **`scx_locked_rq_state` only covers SCX ops.** TRACING programs may call `scx_bpf_cpuperf_set` (an `any` kfunc).
   If such a program runs while the core holds an rq lock outside an SCX op (for example `tp_btf/sched_switch`),
   `scx_locked_rq()` is NULL, so the kfunc would `rq_lock_irqsave()` the rq (9453), which may already be held.
   *Potential deadlock, needs a test.*
4. **`scx_bpf_task_set_slice` / `scx_bpf_task_set_dsq_vtime` (`I1.task_set.unlocked_write`)** write `p->scx.slice`/`dsq_vtime` from any context.
   They check only ownership and take no lock. Likewise `scx_bpf_dsq_insert` called from `ops.dispatch` writes
   `p->scx.slice` of an arbitrary task (8207) without that task's rq lock.
5. **`ops.dump` runs in hard-irq-like context with `scx_dump_lock` held** (6337, irq_work 6481 / SysRq 7814).
   It is nevertheless an UNLOCKED op, so `scx_bpf_dsq_move` (takes task rq lock + dsq lock) and
   `scx_bpf_select_cpu_dfl` (takes `pi_lock`) are allowed there. Only lockdep watches the resulting lock nesting.
6. **Over-broad UNLOCKED group.** `dump`, `cgroup_cancel_move` and `cgroup_set_*` get the UNLOCKED set even though they cannot be sleepable.
   So `scx_bpf_create_dsq` is listed as allowed by `scx_kf_allow_flags[]` but is then rejected by the KF_SLEEPABLE rule.
   This is harmless, but a checker that reads only the allow table would be wrong.
7. **Weak runtime check for `scx_bpf_dump_bstr`**: it compares only the CPU number (9324).
   A TRACING program that runs on the dumping CPU (for example from NMI) passes the check.
8. **lockdep-only assertions** (`scx_bpf_reenqueue_local` 8738, `update_locked_rq` 466, `scx_dsq_insert_preamble` 8102)
   enforce nothing in production kernels.
9. **Stale comment**: `select_cpu_from_kfunc()` (ext_idle.c:934) lists "non-SCX struct_ops" as a truly unlocked caller,
   but the filter rejects SCX kfuncs there (ext.c:9896).
10. **Documentation drift**: `sched-ext.rst:373` says `scx_bpf_dsq_insert()` can't be called with BPF locks held,
    while the kfunc comment (ext.c:8181) says it "doesn't have any locking restrictions". The verifier rule `I1.bpf_spin_lock.no_calls`
    is what actually applies.

Suggested negative tests:
* `scx_bpf_dsq_move_to_local` from `ops.enqueue`: verifier must reject.
* `scx_bpf_reenqueue_local` from `ops.dispatch`: verifier must reject.
* `scx_bpf_select_cpu_dfl` on a foreign task in `ops.select_cpu`: runtime `scx_error`.
* `scx_bpf_locked_rq` from `ops.init`: runtime `scx_error`.
* `scx_bpf_cpuperf_set(other_cpu)` from `ops.tick`: runtime `scx_error`.
* `scx_bpf_dump` outside a dump: runtime `scx_error`.
* `scx_bpf_create_dsq` from non-sleepable `ops.dump`: verifier must reject.

## 3. Proposed schema follow-ups (not expressible in `contracts/catalog.schema.json` yet)

The YAML follows the A2 schema. The following facts live only in this write-up, or in `notes`/`note` strings:

* **Per-callback context model.** The callback → locks-on-entry → allowed-sets table (§1) is callback-centric.
  The schema is kfunc-centric, so the entry locks appear only as `requires.locks[where=callback_entry, callbacks=…]`
  inside each kfunc entry, and only for the callbacks that matter to that entry. A separate `callbacks:` section
  (callback → entry locks, may_sleep, call sites) would let the checker seed entry locksets for *all* callbacks.
* **`may_sleep` / sleepable programs.** The list of ops for which `bpf_scx_check_member()` allows sleepable programs
  (ext.c:7609-7631), and `KF_SLEEPABLE` on `scx_bpf_create_dsq`, are only encoded as a predicate (`prog->sleepable`).
* **Lockdep-only enforcement.** `mechanisms: [lockdep]` exists, but `expected` cannot say "debug-only".
  We do not count lockdep toward `runtime`. Note that the A2 fixture's `I1.dsq_insert.context` does count it and
  says `static+runtime`; it also cites `ext.c:8101` where the `lockdep_assert_irqs_disabled()` is at 8102.
* **Context-dependent lock requirements.** Some kfuncs check a lock conditionally, based on runtime state
  (`SCX_RQ_IN_BALANCE`, `in_select_cpu`, `scx_locked_rq()`). These are written as predicates; the schema has no
  first-class notion of "lock X held iff state Y".
* **Non-struct per-CPU state.** `direct_dispatch_task` and `scx_locked_rq_state` are plain per-CPU variables,
  so they cannot be `objects` (`struct` + `fields`). They are mentioned in descriptions and notes.
