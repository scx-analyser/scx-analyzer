# I3: CPU, affinity and argument validity before scheduling-state writes

Kernel: Linux v7.1, commit `8cd9520d35a6c38db6567e97dd93b1f11f185dc6`. Catalog: `I3.yaml`.

## Statement

When a sched_ext kfunc takes a CPU number, a task or a DSQ id from the BPF scheduler and then modifies shared scheduler state, the check that validates that argument must **dominate** the write on every path from the kfunc. I3 records, for each such write, the guard, the failure edge and the write, with exact lines.

Three dominance shapes occur in v7.1. A guard analysis needs to recognise all three:

| Shape | Pattern | Example |
|---|---|---|
| early return | `if (!guard) return;` ... write | `scx_kick_cpu` 8886-8887 -> 8921 |
| branch | `if (guard) { ... write ... }`, false edge skips to function end | `scx_bpf_cpuperf_set` 9436 -> 9458 |
| fallback | argument replaced (global DSQ), write still happens on another object | `find_dsq_for_dispatch` 1747-1748, `move_task_between_dsqs` 2471-2475 |

The branch shape is the one the C4 guard analysis (PR #54) cannot prove yet: there is no return statement after the failed guard. The write sits inside the then-block instead.

`ops_cpu_valid()` (ext.c:1098-1106) is `__cpu_valid()` (1083-1086: `0 <= cpu < nr_cpu_ids && cpu_possible(cpu)`) or `scx_error()`. It does **not** check that the CPU is online.

Enforcement is runtime everywhere (guard + scx_error, plus a WARN in task_can_run_on_remote_rq 2334). No I3 check is static: the verifier does not see CPU or DSQ-id values.

## Worked example: `scx_bpf_kick_cpu`

```
scx_bpf_kick_cpu(cpu, flags, aux)                ext.c:8945
  guard(rcu); sch = scx_prog_sched(aux)          8949-8950
  if (likely(sch)) scx_kick_cpu(sch, cpu, flags) 8951-8952
scx_kick_cpu                                      8881
  if (!ops_cpu_valid(sch, cpu, NULL))  <- GUARD   8886  (scx_error at 1103 on failure)
      return;                          <- EXIT    8887
  local_irq_save; this_rq = this_rq()             8889-8891
  [bypass: goto out 8899]
  SCX_KICK_IDLE: cpu_rq(cpu) 8907, trylock, maybe goto out 8915
      cpumask_set_cpu(cpu, this_rq->scx.cpus_to_kick_if_idle)  <- WRITE 8919
  else
      cpumask_set_cpu(cpu, this_rq->scx.cpus_to_kick)          <- WRITE 8921
      ... cpus_to_preempt 8924, cpus_to_wait 8926               <- WRITE
  irq_work_queue(...)                             8929
```

Every path from the entry to 8919-8926 goes through 8886, and its false edge leaves the function at 8887. The only other exits before the writes (`goto out` at 8899 and 8915) skip the writes. The written object is the calling CPU's rq (`this_rq`), indexed by the validated `cpu`. No rq lock is needed: irqs are off and the bitmap ops are atomic. `cpu_rq(cpu)` at 8907 is also dominated by the guard. The SCX_KICK_IDLE + PREEMPT/WAIT check at 8909-8910 is a guard that does *not* dominate anything: it calls scx_error and falls through.

## Gaps worth testing

1. **Offline-but-possible CPUs.** `ops_cpu_valid` accepts them. Things to test: `scx_bpf_kick_cpu` on an offline CPU (sets a bit, then the irq work runs), `scx_bpf_cpuperf_set` (writes cpuperf_target and calls cpufreq_update_util on an offline rq), and `scx_bpf_test_and_clear_cpu_idle` (clears the bit; the SMT handling comment at ext_idle.c:93-96 shows offline CPUs need care). For dispatch, offline is caught later, as an event only (2368-2371).
2. **Single-CPU task with a BPF mask** (draft `I3.idle.kfunc_allowed_mask`). Call `__scx_bpf_select_cpu_and(p, mask)` with p pinned to CPU A, `prev_cpu = B` and `B` in mask. Expected per the source: B's idle bit is cleared and B is returned, although B is not in `p->cpus_ptr`.
3. **Deferred DSQ-id validation.** `scx_bpf_dsq_insert*` accept any id. An invalid LOCAL_ON cpu or an unknown user DSQ fails only later, in finish_dispatch / direct_dispatch, with scx_error plus the global DSQ. Test that the task still ends up runnable and that the error is attributed to the right scheduler.
4. **Silent skip in consume_dispatch_q.** With enforce=false, a DSQ whose tasks are all disallowed on this CPU makes `scx_bpf_dsq_move_to_local` return false with no error. Check for starvation.
5. **SCX_KICK_IDLE with PREEMPT/WAIT.** The scheduler is aborted, but the kick still happens.
6. **Guard analysis (C4).** Use `scx_bpf_cpuperf_set` (branch shape) and `find_dsq_for_dispatch` (fallback shape) as regression cases: a checker that only recognises "guard then return" will report them as unprotected.
